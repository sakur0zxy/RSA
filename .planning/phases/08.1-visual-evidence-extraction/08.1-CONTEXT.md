# Phase 08.1: Visual Evidence Extraction - Context

**Gathered:** 2026-05-19  
**Status:** Ready for planning  
**Source:** `$gsd-discuss-phase 8.1` inline discussion, no subagents

<domain>
## Phase Boundary

Phase 8.1 converts Phase 8 `asset_suggestions`, local authorized PDFs, and registered local assets into reviewable visual evidence candidates. It creates candidate figure/table crops, caption candidates, basic OCR summaries, page/region/source trace, confidence/status metadata, and context packets for later LLM-assisted visual analysis.

Phase 8.1 does not perform paper relevance/quality/read-priority scoring, does not generate formal scientific conclusions from figures, does not write formal records, and does not implement advanced curve extraction, advanced table reconstruction, or multimodal claim drafting.
</domain>

<decisions>
## Locked Decisions

### User-Facing Language
- User-facing CLI output, validation errors, templates, packets, warnings, repair hints, and documentation must be Chinese-first.
- YAML keys, CLI flags, status enum values, file identifiers, and code symbols remain stable English.
- Any English field meant for users must have nearby Chinese explanation, usually through `*_zh` fields.

### Default Input Scope
- Default input is `asset_suggestions` plus automatic scanning of authorized PDF pages.
- `asset_suggestions` are processed first; full-PDF scanning is used as a supplement to catch missed visual candidates.
- Missing authorized PDF, broken source file, unreadable PDF, or missing local full text must fail closed with `blocked` or `partial` status and a Chinese reason.
- Default mode must not blindly crop every figure/table in a paper. It should save only candidates that enter the visual evidence candidate list.
- The CLI must preserve expansion modes: `--all-detected` for every detected figure/table, `--pages 3,5-7` for specified pages, and `--asset-suggestions-only` for Phase 8 suggestions only.

### Output Structure
- Use a two-layer output structure:
  - `01_literature/assets/P###/manifest.yaml` records local asset files, crop/OCR artifacts, source path, generated time, and provenance.
  - `visual_evidence_candidates.yaml` records reviewable visual evidence candidates and their evidence metadata.
- File assets and evidence interpretation must stay separate. The manifest answers “where is the file and where did it come from”; the candidate list answers “why this may matter and what state it is in”.
- Candidate records must include source links back to the reading draft, asset manifest, PDF/source ledger, and any local artifact path needed for review.

### Candidate Schema
- Required stable fields include `candidate_id`, `paper_id`, `asset_id`, `visual_type`, `page`, `region_bbox`, `source_rects`, `source_text`, `confidence`, `evidence_level`, `status`, and `source_links`.
- `visual_type` must support `text`, `figure`, `table`, `caption`, `equation`, and `unknown`.
- User-facing explanation fields must include Chinese variants such as `caption_zh`, `ocr_summary_zh`, `evidence_note_zh`, `warning_zh`, and `repair_hint_zh`.
- Add `sentence_id` and `region_id` when a candidate is tied to text or a page region.
- Track `failed_matches` when sentence/region/caption binding fails or partially fails.

### Extraction Depth
- Phase 8.1 should implement basic visual evidence extraction:
  - locate candidate figure/table/caption/equation/text regions;
  - save crop assets;
  - extract caption candidates;
  - run basic OCR or OCR-like text capture where available;
  - record `page`, `region_bbox`, `source_rects`, `source_links`, and Chinese uncertainty notes.
- Phase 8.1 must not implement curve data recovery, advanced table structure understanding, figure numeric value restoration, multimodal image interpretation as final judgment, or figure-driven scientific claim drafts.
- Preserve an `advanced_analysis` extension field with default `not_run` entries for `curve_extraction`, `table_structure`, and `multimodal_interpretation`.

### Confidence And Degradation
- Use conservative degradation: preserve reviewable candidates when useful, but clearly mark risk.
- Suggested status mapping:
  - `detected`: region or visual item detected but not yet cropped.
  - `cropped`: crop asset saved.
  - `ocr_success`: basic OCR/text capture succeeded.
  - `ocr_partial`: crop exists but OCR/text capture is incomplete.
  - `needs_review`: boundary, caption binding, or evidence interpretation is uncertain.
  - `blocked`: no reliable candidate can be produced because source, authorization, PDF, or extraction failed.
  - `not_run`: optional or advanced capability not executed.
- For scanned pages where text extraction is unreliable but a visual candidate exists, set `evidence_level: visual_only`.
- Every degraded item must include `warning_zh` and `repair_hint_zh`.

### LLM Visual Analysis Handoff
- Do not create a separate full phase for LLM-assisted image analysis now.
- Phase 8.1 prepares `visual_context_packet` inputs; Phase 9 performs or consumes LLM visual analysis as part of evidence signals and AI-assisted scoring.
- Each `visual_context_packet` should collect crop path, caption candidate, nearby text, figure/table reference sentences, OCR text, page/region/source trace, and evidence scope.
- Add `llm_visual_analysis` with default `not_run`. If later populated, it must record model, prompt version, evidence scope, Chinese explanation, uncertainty, and source links.
- LLM visual analysis remains staging/review material only and must not bypass formal write gates.

### CLI Workflow
- Add a single main command:
  - `rsa visual extract P001`
- Add explicit control/retry flags:
  - `--all-detected`
  - `--pages 3,5-7`
  - `--asset-suggestions-only`
- Add read-only inspection commands:
  - `rsa visual validate P001`
  - `rsa visual status P001`
- Do not merge visual extraction into `rsa note draft`; Phase 8 and Phase 8.1 boundaries must remain clear.
- Do not require users to manually chain separate `detect`, `crop`, `ocr`, and `packet` commands for the default workflow.

### EasyPaper-Informed Boundaries
- EasyPaper should be treated as a reference for PDF coordinate positioning, visual review, portable knowledge objects, and agent-facing interfaces, not as a Web app architecture to copy.
- In RSA docs, describe this as a “coordinate-level evidence positioning prototype” rather than a complete research evidence chain.
- RSA must maintain its own complete evidence chain: claim/source/page-region/confidence-status/human-review.
- EasyPaper-like findings or portable JSON objects may inform staging/review packets but must never replace formal records such as `paper_index.md`, `literature_map.md`, `research_tables.md`, or approved reading notes.

### Agent Discretion
- The planner may choose the exact internal module split and parser implementation, provided the CLI, schema, Chinese-first outputs, local-only asset handling, and formal-record guardrails above are preserved.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/rsa_cli/assets.py` already defines source record and asset manifest paths, local copy behavior, validation helpers, and Chinese error messages. Phase 8.1 should reuse these conventions rather than inventing a new asset layer.
- `src/rsa_cli/reading_draft.py` already selects PDF sources from `sources/P###.yaml`, records extraction cache under `01_literature/extracted/P###/`, and emits `asset_suggestions` into the reading draft/review packet.
- `src/rsa_cli/cli.py` uses grouped argparse subcommands with Chinese help text and explicit read-only validate/status commands. `rsa visual ...` should follow this style.

### Established Patterns
- User-visible output is Chinese-first while stable schema keys stay English.
- Status-producing commands fail closed and write blocked/partial status records instead of creating normal-looking outputs from missing evidence.
- Binary artifacts and extracted caches are local-only; tracked YAML/Markdown should contain metadata, paths, hashes, summaries, and review status rather than raw copyrighted material or secrets.
- Formal writes are performed only through explicit `rsa formal ...` gates and require human confirmation.

### Integration Points
- Input comes from Phase 8 `asset_suggestions`, source ledger PDF entries, and asset manifest records.
- Output should update or create `01_literature/assets/P###/manifest.yaml` and create a visual candidate file under the paper/notes/assets area chosen by planning.
- Phase 9 will consume visual candidates and `visual_context_packet` entries for evidence signals and AI-assisted scoring.
- Phase 10 will later call `rsa visual extract P###` as one automated workflow step.
- Phase 12 should use `source_links`, `page`, `region_bbox`, and local crop assets for click-back review.
</code_context>

<specifics>
## Specific Ideas

- Candidate mode is the default; all-detected mode is explicit.
- Visual candidates should be useful for supervision, not noisy proof that every detected graphic is important.
- LLM image analysis is desired, but Phase 8.1 only prepares the context and schema. Final fusion belongs in Phase 9.
- EasyPaper influenced the design through PDF coordinates, highlighter metadata, processing status, and reader UI concepts; RSA must adapt those ideas into a traceable harness rather than copy the app.
</specifics>

<deferred>
## Deferred Ideas

- Full LLM-assisted multimodal interpretation and fusion is Phase 9 scope.
- Curve data extraction, numeric value recovery, advanced table reconstruction, visual question answering, and multimodal claim drafting are deferred advanced figure intelligence.
- Complex knowledge graph, flashcards, and full EasyPaper-style Web app features remain outside Phase 8.1.
- Local review workspace for clickable PDF/crop review belongs in Phase 12.
- Claim-level citation hardening belongs in Phase 13.
</deferred>
