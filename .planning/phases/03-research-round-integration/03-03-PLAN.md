<objective>
Implement the formal map application guardrail for Phase 3.

Purpose: make `literature_map.md` writable only through an explicit, human-confirmed CLI path that reads completed round `formal_write_requests`, validates schema and conflicts, and blocks unsafe writes before any formal file changes.

Output: a formal writer module, `rsa formal apply-map` CLI command, tests for approval/schema/conflict blocking, and Chinese user-facing explanations with stable English field names.
</objective>

<scope>
In scope:
- Add or extend `src/rsa_cli/formal.py` to parse `formal_write_requests` from `final_round_summary.md` frontmatter and apply only approved map-row requests.
- Add `rsa formal apply-map --source-round R001_xxx --human-confirmed --confirmed-by "name"` in `src/rsa_cli/cli.py`; optional `--confirmed-at` may be accepted for audit text.
- Reuse Phase 2 metadata validation from `src/rsa_cli/metadata.py` to prove every `paper_id` is formal, verified, and human-confirmed.
- Reuse the Phase 3 map parser/renderer from `src/rsa_cli/map.py` created by 03-02; do not hand-roll ad hoc Markdown string edits when structured helpers exist.
- Validate D-24 to D-27 `formal_write_requests` schema and reject malformed request lists with Chinese errors.
- Validate D-18 to D-23, D-28 to D-34 guardrail decisions in tests and CLI behavior.

Out of scope:
- Do not create new `metadata/P###.yaml` files or allocate `paper_id` values.
- Do not implement `add_metadata` request application; report it as pending metadata-gate work if encountered.
- Do not change candidate search, PDF handling, reading notes, web search, or thesis/review prose generation.
- Do not overwrite or auto-merge existing formal rows on conflict.
- Do not make `validate`, `generate`, or `propose` commands write formal records.
</scope>

<threat_model>
- T-03-03-01 Unapproved formal write: a map row enters `literature_map.md` without explicit user approval. Mitigate by requiring CLI action plus `--human-confirmed` and non-empty `--confirmed-by`; fail before writing if either is missing.
- T-03-03-02 Round-derived write from unsafe source: an agent output proposes formal writes from a draft, blocked, or unconfirmed round. Mitigate by requiring source `final_round_summary.md` status `completed`, `human_confirmed: true`, non-empty `confirmed_by`, non-empty `confirmed_at`, and all declared `included_files` present.
- T-03-03-03 Candidate-to-formal bypass: `formal_write_requests` may contain candidate titles or `add_metadata` requests that could skip Phase 2 metadata gates. Mitigate by letting `apply-map` consume only `add_map_row` requests with existing `paper_id`; reject candidate-only map rows and never create new IDs.
- T-03-03-04 Conflict or overwrite: an applied row duplicates or conflicts with an existing formal map row. Mitigate by preflighting all rows against the parsed map before writing; if any conflict exists, print Chinese diagnostics and leave `literature_map.md` byte-for-byte unchanged.
- T-03-03-05 Language/key drift: translating fields could break scripts, or English-only errors could confuse the user. Mitigate by keeping field names and CLI flags in English while all user-readable help, errors, and summaries explain the issue in Chinese.
</threat_model>
