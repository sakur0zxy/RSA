# Phase 11-01 Plan: Campaign Run State And Metadata Intake Schema

## Objective

<objective>
Add the Phase 11 campaign run-state, metadata intake request and formal write request data model beside existing campaign YAML files. This plan establishes the durable staging/review records that later pipeline execution and review queue reporting will consume, without running workflows or writing formal metadata.
</objective>

## Must Haves

<must_haves>
<truth id="D-01">D-01: Campaign item 分为 `linked` 和 `queued`；`linked` 可以进入 Phase 10 workflow，`queued` 只能生成 metadata intake request。</truth>
<truth id="D-02">D-02: `queued` 条目可以自动整理、去重、轻量补全和送入待审队列，但正式 metadata 写入必须经过 metadata gate 和人工确认。</truth>
<truth id="D-03">D-03: 轻量 metadata enrichment 只写入 `candidate_metadata`，保留来源、置信度和中文说明，不作为已核验 formal fact。</truth>
<truth id="D-04">D-04: Metadata intake request v1 存放在 `01_literature/campaigns/C001_metadata_requests.yaml`。</truth>
<truth id="D-05">D-05: 每条 metadata request 必须有 `request_id`、`source_campaign_id`、`queued_item_id`、`status`、`candidate_metadata`、`created_at`。</truth>
<truth id="D-06">D-06: Metadata request 状态为 `auto_triaged`、`needs_review`、`accepted`、`rejected`、`merged`；默认是 `auto_triaged`。</truth>
<truth id="D-07">D-07: `needs_review` 只用于人工重点审阅或系统发现低置信、重复、缺 metadata、来源不清等高风险情况。</truth>
<truth id="D-08">D-08: Metadata request 最小 triage 字段为 `triage_confidence`、`recommended_action`、`triage_reason_zh`、`formal_write_allowed: false`。</truth>
<truth id="D-09">D-09: Request 必须按未来可迁移到 `01_literature/metadata_requests/MR###.yaml` 的独立对象设计。</truth>
<truth id="D-10">D-10: Metadata intake request 被 `accepted` 后，Phase 11 只生成可审阅 `formal_write_request`，不写 `metadata/P###.yaml`。</truth>
<truth id="D-11">D-11: `formal_write_request` v1 放在 review queue 或 metadata request 旁边，并与 `C001_review_queue.yaml` / `C001_metadata_requests.yaml` 互相引用。</truth>
<truth id="D-12">D-12: `formal_write_request` 必须可迁移为独立对象，并保留稳定 id、来源 campaign/item、目标 formal record、状态和中文理由。</truth>
<truth id="D-13">D-13: `formal_write_request` 状态为 `pending_human_approval`、`approved_for_write`、`rejected`、`applied`。</truth>
<truth id="D-14">D-14: Phase 11 不增加 formal apply 子命令，也不自动执行 `approved_for_write`。</truth>
<truth id="D-32">D-32: Run state 和报告 v1 放在 `C001_run.yaml`、`C001_review_queue.yaml`、`C001_batch_report.md`。</truth>
<truth id="D-33">D-33: 后续可迁移到 `01_literature/campaign_runs/C001/RUN-###.yaml`，当前 campaign 旁边文件只保留当前状态或索引。</truth>
<truth id="D-36">D-36: `C001.yaml` 只追加轻量状态索引，不写完整运行结果。</truth>
<truth id="D-37">D-37: Phase 11 v1 是同步 CLI，但 run state 预留 `worker_mode: sync_cli`、`task_id: null`、`worker_status: not_used`。</truth>
<truth id="D-45">D-45: Phase 11 拆成 3 个 plans，本计划负责 metadata intake request 和 campaign run state/schema。</truth>
<truth id="D-46">D-46: Phase 11 v1 测试必须覆盖 metadata intake、run state 和 formal write 边界。</truth>
</must_haves>

<action>
Implement metadata intake request creation for queued campaign items:
- create one request per eligible `queued` item;
- default status `auto_triaged`;

- derive `candidate_metadata` from campaign item title/author/year/doi/url/topic fields;

- Requests include `formal_write_allowed: false`.
- Duplicate reruns do not create duplicate requests.
- Linked items do not create metadata intake requests.
- Request files are UTF-8 YAML with stable English keys and Chinese explanations.
</acceptance_criteria>

<threat_model>
- **Threat:** Queued candidates become formal metadata. **Mitigation:** metadata intake writes staging files only and sets `formal_write_allowed: false`.
- **Threat:** Request objects are hard to migrate later. **Mitigation:** stable ids, source links and object-shaped schema.
- **Threat:** Run results bloat `C001.yaml`. **Mitigation:** store run/report/request files beside campaign and keep `C001.yaml` as an index.
- **Threat:** Formal write request status is confused with review queue decision. **Mitigation:** separate status enums and tests.
</threat_model>
